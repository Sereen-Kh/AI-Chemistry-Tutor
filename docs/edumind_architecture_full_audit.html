🔴 The 5 most critical problems right now
1. No Celery Beat in Docker — Notification reminders are fully modelled and scheduled, but they will NEVER fire because Beat is not in `docker-compose.yml`. All the notification work is dead unless this is added.

2. `/chat/ask` does not persist — The one-shot endpoint used by the frontend chat does not save messages or citations. Students think they have a history, but the backend stores nothing from this endpoint.

3. Silent mock fallback in frontend chat — When the AI API fails, the frontend silently returns a fake mock answer. Students receive fabricated chemistry answers with no indication they are not real. This is a trust and safety issue.

4. Frontend and backend are misaligned on 5 domains — Quiz, flashcards, study-plan generation, homework upload, and dashboard all have either missing backend routes or mismatched schemas. These pages are broken or mock-backed.

5. No `/dashboard` aggregate endpoint — The dashboard (the first thing every student sees) shows static hardcoded data. Nothing is real: progress, streak, recommendations, XP — all fake.

🔴 Critical — production-blocking
🔥
No Celery Beat container in docker-compose.yml
All scheduled reminders, study-plan nudges, and notification tasks will never fire
Critical▶
Celery Beat missing from docker-compose.yml
The notification_tasks.py and reminder_service.py are fully implemented. But without Beat running, no periodic task ever executes. Students never receive study reminders, streak alerts, exam countdowns, or weekly summaries — even though all the code exists.
ADD to docker-compose.yml: celery-beat: command: celery -A app.workers.celery_app beat --loglevel=info depends_on: [postgres, redis]
💬
/chat/ask is one-shot — no persistence, no citations stored
Students use this endpoint but nothing is saved to the database
Critical▶
Chat messages not persisted from /chat/ask
The frontend uses /chat/ask for the main chat flow. But this endpoint does not create a ChatSession or save ChatMessages. Session endpoints exist and DO persist — but the frontend isn't using them. The student thinks they have history, but the backend has nothing. Also: ChatMessage has no structured citations column — source chunk references are returned in the response but never stored.
Fix A: Make /chat/ask accept optional session_id and persist messages Fix B: Add citations JSONB column to ChatMessage model + Alembic migration Fix C: Align frontend to use /chat/sessions flow
📊
No /dashboard aggregate endpoint
The most important page for retention shows 100% static fake data
Critical▶
Dashboard endpoint missing — all data hardcoded in frontend
The frontend dashboard shows streak, XP, progress %, today's lesson, recommendations, weak topics, exam countdown. All of these come from hardcoded values in the component. The backend has all the data (UserProgress, Achievement, StudyPlan, QuizAttempt, LessonProgress) but no single GET /dashboard endpoint that aggregates it.
Create: GET /api/v1/dashboard Returns: { streak_days, xp, level, today_lesson, overall_pct, chapters_progress[], weak_topics[], recommendations[], exam_days_remaining } Cache in Redis per user, TTL=5min
📸
Homework image upload — image_path only, no multipart
Mobile/web users cannot upload a photo of their homework
Critical▶
Homework solver accepts image_path string, not a real file
The homework schema takes an image_path field — a server-side path string. No web or mobile client can use this. It only works if files are already on the server disk. Need a standard multipart/form-data upload endpoint that accepts the image, stores it in S3/R2, and returns a URL that the homework solver can then process.
Add: POST /api/v1/homework/upload (multipart/form-data) Returns: { image_url: str, homework_id: int } Backend: store in Cloudflare R2, pass URL to Gemini vision
🟡 High — blocking features
📱
DeviceToken model exists — zero API endpoints
Push notifications structurally impossible without device registration
High▶
No POST/DELETE /device-tokens API
DeviceToken model in device.py has user_id, token, platform. But no router was found for registering or deleting device tokens. Without this, the mobile app and web frontend cannot register for FCM push notifications. Even if Celery Beat is fixed, push notifications will never reach anyone.
Add router: /api/v1/devices POST /api/v1/devices/register → save FCM token DELETE /api/v1/devices/{token} → remove on logout GET /api/v1/devices → list user's registered devices
♻️
RAG cache not invalidated after re-embedding
After a re-embed job, students get stale cached results for hours
High▶
Redis RAG cache never invalidated after ingestion/re-embedding
rag.py uses Redis to cache retrieval results. But when rag_reembed.py finishes re-embedding chunks with a new model, the Redis cache still holds the old results from the previous embeddings. Students will get stale answers for up to the cache TTL (likely 1 hour) after an ingestion update.
In rag_tasks.py, after re-embed completes: await redis_client.delete_pattern("rag:*") or flush only affected source keys
💼
chat_service.py is 1800+ lines — unmaintainable monolith
Mixes routing, retrieval, prompts, media routing, and local fallback in one file
High▶
chat_service.py mixes 5 different concerns in one file
The file contains: answer routing logic, RAG retrieval calls, prompt building, media format routing, dictionary-based fallback logic, and local mock responses. This means a bug in prompt building can accidentally break media routing, and a change to RAG retrieval breaks dictionary lookup. Any engineer touching this file risks breaking everything else.
Split into: tutor_prompt_builder.py (already exists — use it) answer_router.py (media/format routing) chat_history_service.py (session persistence) chat_service.py (thin orchestrator only)
🔄
Ingestion jobs not durable — lost on server restart
In-memory _TASKS dict means any restart wipes all job status
High▶
Ingestion progress tracked in memory, not DB
/admin/ingestion/start uses FastAPI BackgroundTasks + in-memory _TASKS dict for progress. If the backend restarts (crash, deploy, OOM) during a 96-page ingestion job, all progress is lost and the admin doesn't know which pages were processed. IngestionJob and IngestionPage models exist in DB — they should be the source of truth.
Move ingestion to Celery task (not BackgroundTasks) Update IngestionJob.status in DB after each page Remove in-memory _TASKS dict entirely
🔴 Critical — trust and data integrity
🤥
Silent mock fallback in aiApi.ask — students get fake chemistry answers
When API fails, frontend silently returns fabricated AI responses
Critical▶
aiApi.ts catches API errors and returns mock chemistry answers
When the backend AI endpoint fails (network error, Gemini quota, backend crash), the frontend catches the error and returns a pre-written fake answer about water molecules or chemical bonds. The student sees a confident-looking AI answer with no indication it is fake. For a chemistry tutor, this is a serious accuracy and trust problem — a student could learn wrong chemistry from a mock response.
Remove mock fallback entirely from aiApi.ask Replace with: show ErrorBanner "المساعد غير متاح الآن، يرجى المحاولة لاحقاً" Never show fake AI content to students
🏠
Dashboard shows 100% static data — no backend calls at all
Streak, XP, progress, lessons — all hardcoded in the component
Critical▶
DashboardPage in App.tsx contains hardcoded numbers
The most important page for student motivation (first screen every day) shows: "36% progress", "7 day streak", "87% quiz average", "today's lesson: Covalent bonds". None of these are real. They are hardcoded JSX values. This means every student sees the same dashboard regardless of what they've actually done.
1. Create GET /api/v1/dashboard backend endpoint first 2. Create dashboardApi.ts adapter 3. Replace hardcoded values with useEffect + API call 4. Add LoadingSkeleton + ErrorBanner states
🟡 High — blocking student workflows
📋
No global state management — everything in localStorage
No Zustand, no Redux, no React Query — server state is not managed
High▶
State management gap across the entire frontend
The frontend stores auth tokens and preferences in localStorage via storage.ts. There is no global state library (Zustand, Redux, React Query). This means: API data is re-fetched on every render, loading states are inconsistent across pages, user XP/streak changes in one page don't update in the sidebar, and there is no single source of truth for auth state. As features grow, this will become a serious bug surface.
Add React Query v5 for server state (lessons, chat, progress) Add Zustand for client state (auth, preferences, active session) Migrate auth from localStorage to Zustand with persistence middleware

🔴 RAG gaps
🔢
Embedding model inconsistency — gemini-embedding-001 vs text-embedding-004
Different dimensions would corrupt the vector index silently
Critical▶
Two embedding models referenced across the codebase
The backend report says gemini-embedding-001 is current. The codebase analysis says both gemini-embedding-001 and text-embedding-004 are referenced in different places. These models produce DIFFERENT vector dimensions (gemini-embedding-001 = 768, text-embedding-004 = 768 too — but they are semantically different models). If chunks are embedded with one model and queries use another, similarity scores will be meaningless. Also: local sentence-transformers fallback is commented out, so clean installs silently fall back to hash embeddings.
1. Pick ONE model: gemini-embedding-001 (current production) 2. Remove all references to text-embedding-004 3. Add startup check: if embedding_model != active model → block 4. Remove hash fallback from production code entirely 5. Update .env.example and README to remove OpenAI references
📉
Scoring weights still at 0.35 vector / 0.65 lexical (from screenshots)
Arabic morphology breaks lexical matching — students get 28-44% similarity scores
Critical▶
Hybrid scoring weights need to be flipped for Arabic
Based on the screenshots from previous analysis: students see similarity scores of 28-44%. This is caused by the 0.65 lexical weight — Arabic morphology means "الأملاح" doesn't match "أملاح" in keyword matching, collapsing the lexical score to near zero and dragging the hybrid score down. All the advanced RAG features (HyDE, multi-query, reranking) are undermined by this one weight misconfiguration.
In rag.py: VECTOR_WEIGHT = 0.75 # was 0.35 LEXICAL_WEIGHT = 0.25 # was 0.65 MIN_SIMILARITY = 0.55 # was 0.25
📊
RAG evaluation not in CI — no quality gate for deploys
A bad re-embedding could ship to production without detection
High▶
evaluate_rag.py exists but is not wired into CI/CD pipeline
The evaluation runner exists and can produce a score. But it is not run as part of GitHub Actions or any deploy pipeline. This means a bad re-embedding job (wrong model, wrong dimension, corrupted chunks) can be deployed to production and students will get worse answers for days before anyone notices.
Add to .github/workflows/ci.yml: - name: RAG quality gate run: python scripts/evaluate_rag.py --threshold 0.65 --fail-below # Fail CI if RAG score drops below 65%

What makes EduMind architecturally strong already
The Interactive Solver is the real differentiator. Most AI tutors are RAG chatbots. EduMind already has a step-by-step guided solver that validates numeric chemistry, tracks misconceptions (MisconceptionEvent model), updates skill mastery (SkillMastery model), and could generate quizzes from weak topics. This is architecturally ahead of 90% of AI tutoring products. The priority is to get it working reliably, localized, and expanded beyond concentration problems.

The RAG pipeline is genuinely sophisticated. HyDE + multi-query + re-ranking in a single pipeline, with a dual-source textbook + solution book, is a strong technical foundation. The main issues are configuration (weights, model consistency) not design.

The data model is comprehensive. 35+ models covering every educational domain: curriculum, progress, gamification, interactive solving, misconceptions, billing, devices, notifications. The schema design is sound. The gaps are in the API surface, not the data model.
The one sentence summary
EduMind has a strong architecture and the right ideas — the database is comprehensive, the RAG pipeline is sophisticated, and the Interactive Solver is genuinely differentiated — but it is being held back by 6 critical configuration bugs (Celery Beat missing, mock fallback, wrong RAG weights, no /dashboard, no chat persistence, embedding model inconsistency) that must be fixed before any new features are added.
